## 1️⃣ 원인 분석  

| 가능성 | 설명 | 근거 |
|--------|------|------|
| **페이징 로직 오류** | 화면에 전달되는 `resultList` 가 페이지당 10건(`pageSize = 10`) 으로 제한돼 있지만, `totalCount` 는 전체 건수(18건) 를 그대로 반환하고 있습니다. 따라서 “전체 18건”이라는 카운트는 맞지만 실제 리스트는 첫 페이지 10건만 보여지는 상황이 됩니다. | `PolicySearchPSI.java` 에서는 `model.addAttribute("resultList", resultList);` 로 리스트를 전달하고, `totalCount` 만 별도로 전달하고 있습니다. 페이지 사이즈가 고정돼 있거나 `offset/limit` 계산이 잘못되면 이런 현상이 발생합니다. |
| **DAO / 쿼리 제한** | DB 조회 메서드가 `SELECT … LIMIT 10` 형태로 고정돼 있거나, `Pageable` 객체가 잘못 설정돼 있어 전체 건수를 구하는 별도 쿼리와 실제 데이터 조회 쿼리의 결과가 일치하지 않을 수 있습니다. | `totalCount` 를 별도 카운트 쿼리로 구하고, 실제 데이터는 `LIMIT` 로 제한하는 전형적인 패턴에서 흔히 발생합니다. |
| **프론트‑엔드 페이지네이션 설정 오류** | JSP/Thymeleaf 등 뷰에서 페이지네이션 UI는 전체 건수를 기준으로 페이지 수를 계산하지만, 실제 데이터 바인딩이 첫 페이지(10건)만 고정돼 있을 경우 “총 18건”이라고 표시되면서 리스트는 10건만 보이게 됩니다. | `model.addAttribute("totalCount", totalCount);` 로 전체 건수를 전달했지만, `resultList` 가 페이지 전환 시 갱신되지 않을 경우 이런 UI 불일치가 나타납니다. |
| **잘못된 기본값** | `PolicySearchResultVO` 의 `totalCount` 필드가 페이징용으로 사용되는데, 서비스 로직에서 `totalCount` 를 페이지당 건수와 혼동해 설정했을 가능성. | `PolicySearchResultVO` 에 “전체 건수 (페이징용)” 라는 주석이 있지만, 실제 코드에서 `totalCount` 를 페이지 사이즈와 혼용했을 경우 발생합니다. |

**핵심 메커니즘**  
1. **전체 건수** (`totalCount`) 는 올바르게 계산 → 18건.  
2. **데이터 리스트** (`resultList`) 가 `LIMIT 10` 혹은 고정된 `pageSize` 로만 조회 → 10건만 반환.  
3. **뷰** 에서는 `totalCount` 를 그대로 표시하지만, `resultList` 가 전체를 포함하지 않아 불일치가 발생.

## 3️⃣ 해결 방법 (우선순위)

1. **페이징 로직 검증 및 수정**  
   - `PolicySearchPSI` 혹은 서비스 레이어에서 `pageSize`, `pageNumber`(또는 `offset`) 를 올바르게 계산하고, `resultList` 를 해당 페이지에 맞게 조회하도록 수정합니다.  
   - 전체 건수와 현재 페이지 데이터를 동시에 반환하는 DTO(예: `PageResult<T>`) 를 도입해 일관성을 확보합니다.

2. **DAO/Mapper 쿼리 점검**  
   - 전체 건수(`SELECT COUNT(*)`) 와 실제 데이터 조회(`SELECT … LIMIT ?, ?`) 가 동일한 조건(검색 파라미터) 을 사용하고 있는지 확인합니다.  
   - `LIMIT` 값이 고정돼 있지 않도록 `pageSize` 파라미터를 바인딩합니다.

3. **프론트‑엔드 페이지네이션 연동**  
   - 뷰에서 페이지 이동 시 현재 페이지 번호를 서버에 전달하고, 서버가 해당 페이지 데이터를 반환하도록 구현합니다.  
   - 페이지 네비게이션 UI가 `totalCount` 와 `pageSize` 로 전체 페이지 수를 정확히 계산하도록 검증합니다.

4. **테스트 케이스 추가**  
   - **경계값 테스트**: 전체 건수가 `pageSize` 이하, `pageSize` 배수, 배수가 아닌 경우 모두 정상 동작하는지 검증.  
   - **다중 페이지 조회**: 2페이지 이상으로 넘어가는 경우 `resultList` 가 올바른 레코드를 반환하는지 확인.

5. **로그·모니터링 강화**  
   - 조회 시 `totalCount`, `pageSize`, `offset`, 반환된 `resultList.size()` 를 로그에 남겨 추후 문제 발생 시 빠르게 원인 파악이 가능하도록 합니다.

@GetMapping("/policy/search")
public String searchPolicy(SearchVO searchVO,
                           @RequestParam(defaultValue = "1") int page,
                           Model model) {

    int pageSize = 10; // 혹은 설정값
    PageResult<PolicySearchResultVO> pageResult =
            policySearchService.searchPolicy(searchVO, page, pageSize);

### 정리  

- **근본 원인**: 페이지네이션 로직(특히 `LIMIT/OFFSET` 혹은 `pageSize` 고정)과 전체 건수 반환이 일치하지 않아 화면에 10건만 표시되는 현상.  
- **영향**: 사용자 신뢰도 저하, 업무 효율 감소, 규제 위험 등 고위험군.  
- **핵심 해결**: 페이지 파라미터를 정확히 전달·계산하고, DAO 쿼리와 서비스 로직을 일관되게 수정.  
- **예방**: 코드 리뷰·표준 DTO·자동화 테스트·로그·모니터링을 통해 동일 패턴 재발 방지.  

위 내용대로 검토·수정 후, 테스트 환경에서 전체 건수와 페이지 전환이 정상적으로 동작하는지 확인하시기 바랍니다. 필요 시 추가적인 로그를 남겨 추적성을 높이면 문제 재발 시 빠른 원인 파악이 가능합니다.
