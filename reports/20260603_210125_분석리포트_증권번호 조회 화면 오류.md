## 1️⃣ 근본 원인 상세 분석  

| 구분 | 가능성 있는 원인 | 설명 |
|------|----------------|------|
| **① UI‑Request** | 페이지 사이즈(`pageSize`)가 고정값 10으로 전송 | “전체 조회”라 하더라도 프론트엔드가 `pageSize=10`을 그대로 보내면 백엔드는 첫 페이지만 반환합니다. |
| **② Service‑Layer** | `pageNumber`·`pageSize` 파라미터를 무시하고 `limit 10`을 하드코딩 | 서비스 메서드가 `PageRequest` 객체를 받지 않거나, 기본값을 10으로 고정해 두었을 가능성. |
| **③ DAO / Mapper** | **COUNT** 쿼리와 **SELECT** 쿼리 조건이 불일치 | `SELECT count(*)` 은 전체 조건을 반영하지만, 실제 데이터 조회 쿼리는 `WHERE … LIMIT 10` 만 적용돼 결과가 10건에 제한됩니다. |
| **④ Pagination Utility** | 페이지 계산 로직(`totalPages = ceil(totalCount / pageSize)`)은 정상이나, **데이터 리스트**를 `pageSize` 로 잘라서 반환 | 즉, `totalCount`는 올바르게 구했지만, 반환 리스트는 첫 페이지만 포함. |
| **⑤ 캐시 / 인터셉터** | 이전 요청 결과가 캐시돼 `totalCount`만 최신, 리스트는 오래된 10건 | 캐시 정책이 잘못 설정돼 전체 건수는 최신이지만 리스트는 오래된 페이지 결과가 반환될 수 있습니다. |

> **가장 흔한 시나리오**  
> - 프론트엔드에서 “전체 조회”를 의미하는 별도 플래그(`all=true`)를 보내지 않음 → 백엔드가 기본 페이지 사이즈(10)로 동작.  
> - 서비스 메서드가 `pageSize` 파라미터를 무시하고 `PageRequest.of(0, 10)`을 강제 사용.

## 2️⃣ 실용적인 해결 방법 (우선순위)

| 순위 | 작업 내용 | 기대 효과 | 구현 시 주의점 |
|------|-----------|-----------|----------------|
| **1** | **UI‑Request 검증** – “전체 조회” 시 `pageSize` 를 `Integer.MAX_VALUE` 혹은 `0`(전체) 로 전송하도록 프론트엔드 로직 수정 | 백엔드가 제한 없이 전체 데이터를 조회하도록 보장 | API 명세에 `all=true` 플래그를 추가하고, 프론트엔드에서 해당 플래그가 있으면 `pageSize` 를 무시하도록 구현 |
| **2** | **Service‑Layer 파라미터 전달** – `pageSize` 가 `null` 혹은 `0`이면 `Integer.MAX_VALUE` 로 변환 후 DAO 호출 | 서비스가 UI 의도대로 전체 데이터를 요청 | 기존 `PageRequest` 생성 로직을 `if (size <= 0) size = Integer.MAX_VALUE;` 로 보완 |
| **3** | **DAO / Mapper 쿼리 점검** – `SELECT … LIMIT :offset, :limit` 구문이 `limit` 값에 따라 동작하도록 수정. `limit` 가 `null`/`0`이면 제한을 두지 않음 | 실제 DB에서 전체 레코드가 반환됨 | MyBatis / JPA 등 사용 중인 ORM 에 따라 `@SelectProvider` 혹은 `CriteriaBuilder` 에 조건 추가 |
| **4** | **총 건수와 리스트 일관성 검증** – `totalCount` 와 `resultList.size()` 가 `pageSize` 와 일치하는지 단위 테스트 추가 | 동일한 조건으로 COUNT와 SELECT가 일관된 결과를 반환하도록 보장 | 테스트 케이스에 `pageSize=0`(전체) 상황 포함 |
| **5** | **캐시 정책 재검토** – 리스트와 카운트가 동일한 키를 사용해 캐시되지 않도록 분리 | 오래된 리스트가 표시되는 현상 방지 | 캐시 키에 `pageSize`·`pageNumber`·`allFlag` 포함 |
| **6** | **로그/모니터링 강화** – 페이징 파라미터와 반환 건수를 로그에 남겨 추후 재현 가능하도록 함 | 문제 재발 시 빠른 원인 파악 | `log.info("[PolicySearch] page={}, size={}, total={}, returned={}", page, size, total, list.size());` |

> **핵심**은 “전체 조회”라는 요구를 **백엔드에 명확히 전달**하고, **백엔드가 이를 무시하지 않도록** 하는 것입니다.

## 2️⃣ 근본 원인 분석  

| 가능성 | 설명 | 근거 |
|--------|------|------|
| **① 페이지네이션 로직 오류** | 조회 로직에서 `limit`(또는 `pageSize`)가 고정값 10으로 설정돼 있어 실제 데이터 전체를 가져오지 못함. 하지만 전체 건수(`totalCount`)는 별도 `COUNT(*)` 쿼리로 정확히 계산하고 있기 때문에 “총 18건”은 올바르게 표시됨. | “10건만 확인되고, 총 18건”이라는 현상은 **데이터는 2가지 흐름**(목록 조회 + 전체 건수 조회)으로 처리될 때 흔히 나타나는 패턴. |
| **② `ResultSet` 처리 중 조기 종료** | `ResultSet`을 순회하면서 `while (rs.next())` 대신 `if (rs.next())` 혹은 `break`가 들어가 있어 첫 10건만 리스트에 추가됨. | 코드가 `ResultSet`을 직접 다루는 경우(예: `JdbcTemplate` 사용) 이런 실수가 발생하기 쉬움. |
| **③ 프론트엔드 페이징 설정 불일치** | 백엔드에서 전체 데이터를 반환했지만, 프론트엔드(예: Angular, React)에서 `pageSize: 10` 으로 고정해 UI에 10건만 렌더링. 총 건수는 백엔드 응답(`totalElements`)을 그대로 사용. | UI와 API 스펙이 맞지 않을 때 흔히 보이는 현상. |
| **④ 캐시/멀티스레드 동시성 문제** | 첫 번째 요청에서 10건만 캐시하고, 이후 `totalCount`만 최신값으로 업데이트된 경우. | 복합적인 캐시 로직이 있는 경우 가능하지만, 발생 빈도는 낮음. |

위 4가지 중 **① 페이지네이션 로직 오류**가 가장 흔하고, 현재 제공된 파일(`PolicySearchDSIImpl.java`)이 **DSI(Data Service Interface) 구현**이라면 DB 접근·쿼리 작성 부분에 해당 로직이 존재할 가능성이 높습니다.

## 6️⃣ 참고용 코드 예시 (수동 적용용)

아래 예시는 **Spring JDBC** 기반 구현에서 페이지네이션 파라미터를 안전하게 처리하는 방법입니다. 실제 프로젝트에 맞게 `PolicySearchDSIImpl` 내부에 적용해 주세요.

```java
// ---------------------------------------------------
// 1) 파라미터 검증 및 기본값 설정
// ---------------------------------------------------
public List<PolicyDto> searchPolicies(SearchCondition cond) {
    // UI에서 전달된 pageSize가 없거나 0이면 전체 조회(또는 기본값 20)
    int pageSize = (cond.getPageSize() == null || cond.getPageSize() <= 0)
            ? Integer.MAX_VALUE   // 전체 조회
            : cond.getPageSize();

    int offset = (cond.getPage() == null || cond.getPage() <= 1)
            ? 0
            : (cond.getPage() - 1) * pageSize;

    // ---------------------------------------------------
    // 2) 목록 조회 쿼리
    // ---------------------------------------------------
    String sqlList = "SELECT p.* FROM policy p "
                   + "WHERE p.policy_no LIKE :policyNo "
                   + "ORDER BY p.policy_no ASC "
                   + "LIMIT :limit OFFSET :offset";

    Map<String, Object> params = new HashMap<>();
    params.put("policyNo", cond.getPolicyNo() + "%");
    params.put("limit", pageSize);
    params.put("offset", offset);

    List<PolicyDto> list = jdbcTemplate.query(sqlList, params, new PolicyRowMapper());

    // ---------------------------------------------------
    // 3) 전체 건수 조회 (조건은 동일하게)
    // ---------------------------------------------------
    String sqlCount = "SELECT COUNT(*) FROM policy p "
                    + "WHERE p.policy_no LIKE :policyNo";

    int totalCount = jdbcTemplate.queryForObject(sqlCount, Collections.singletonMap("policyNo", cond.getPolicyNo() + "%"), Integer.class);

    // ---------------------------------------------------
    // 4) 결과 포장 (프론트엔드가 기대하는 형태)
    // ---------------------------------------------------
    SearchResult<PolicyDto> result = new SearchResult<>();
    result.setTotalElements(totalCount);
    result.setContent(list);
    result.setPage(cond.getPage() == null ? 1 : cond.getPage());
    result.setPageSize(pageSize == Integer.MAX_VALUE ? totalCount : pageSize);
    return result;
}
```

> **핵심 포인트**  
> - `pageSize`가 `null`/`0`이면 **전체 조회**(`Integer.MAX_VALUE`) 혹은 비즈니스에 맞는 기본값을 사용합니다.  
> - `LIMIT`와 `OFFSET`을 **동일 파라미터**(`pageSize`, `offset`)로 전달해 리스트와 카운트 쿼리가 일관되게 동작하도록 합니다.  
> - 반환 객체(`SearchResult`)에 `totalElements`와 `content`를 모두 포함시켜 프론트엔드가 **총 건수와 실제 데이터**를 동시에 사용할 수 있게 합니다.

## 7️⃣ 마무리  

1. **가장 먼저** `PolicySearchDSIImpl` 내부에서 `limit`/`pageSize`가 고정값 10으로 설정돼 있지는 않은지 확인하고, 위와 같은 **동적 파라미터 처리** 로직으로 교체합니다.
