## 🛠️ 2️⃣ 실용적인 해결 방안 (우선순위)

1. **페이징 로직 전체 검증 및 수정**  
   - **서비스/DAO**:  
     - 전체 건수(`totalCount`)를 구하는 **별도 카운트 쿼리**와 실제 데이터 조회 쿼리를 **동일 조건**으로 실행했는지 확인.  
     - `PageRequest`(Spring Data) 혹은 `RowBounds`(MyBatis) 등 프레임워크가 제공하는 페이지 객체를 사용해 **동적 `limit/offset`**을 전달하도록 수정.  
   - **예시 (Spring Data JPA)**  
     ```java
     Pageable pageable = PageRequest.of(page, size, Sort.by("policyNo"));
     Page<Policy> page = policyRepository.findAll(spec, pageable);
     
     // 반환 객체
     PagingResult result = new PagingResult();
     result.setTotalCount(page.getTotalElements());   // 전체 건수
     result.setDataList(page.getContent());           // 현재 페이지 데이터
     ```
   - **예시 (MyBatis)**  
     ```xml
     SELECT * FROM policy
     WHERE ${conditions}
     ORDER BY policy_no
     LIMIT #{limit} OFFSET #{offset}
     ```

2. **프론트엔드 페이지네이션 로직 점검**  
   - **전체 조회** 버튼 클릭 시 `page=0, size=totalCount` 혹은 `size=전체 건수` 로 요청을 보내도록 UI 로직을 수정.  
   - **Vue/React/Angular** 등 사용 중인 프레임워크에서 **pagination component**가 `totalCount`와 `pageSize`를 올바르게 바인딩하고 있는지 확인.  

3. **DTO/VO 매핑 오류 방지**  
   - `PagingResult`(또는 `PageInfo`) 클래스에 **`List<T> dataList`** 를 직접 복사하지 말고, **서비스 레이어에서 그대로 전달**하도록 구현.  
   - 불필요한 `subList` 혹은 `Collections.copy` 로 인한 데이터 절삭 로직을 제거.  

4. **로그 및 모니터링 추가**  
   - **쿼리 실행 로그**와 **응답 페이징 정보**(`totalCount`, `pageSize`, `currentPage`, `dataList.size`)를 DEBUG 레벨에 출력해, 실제 반환값을 눈으로 확인할 수 있게 함.  

5. **테스트 코드 보강**  
   - **단위 테스트**: 전체 건수 0~100건을 대상으로 `pageSize`가 10, 20, 50 등 다양한 경우에 `totalCount`와 `dataList.size`가 일치하는지 검증.  
   - **통합 테스트**: UI → API → DB 흐름 전체를 시뮬레이션해 “전체 조회” 버튼을 눌렀을 때 화면에 18건이 모두 표시되는지 자동 검증.

아래에서는 **근본 원인**을 상세히 파악하고, **실용적인 해결 방안**을 우선순위별로 제시하며, **재발 방지**와 **영향·심각도** 평가까지 정리했습니다.

## 1️⃣ 근본 원인 상세 분석  

| 구분 | 가능성 | 설명 |
|------|--------|------|
| **① 페이징 파라미터 전달 오류** | UI → Controller → Service → Repository 로 흐르는 `pageSize`, `pageNumber` 값이 잘못 전달되거나 기본값(10)으로 고정돼 있음 | UI에서 “전체 조회” 시 `pageSize`를 `0`(또는 `null`) 로 보내야 전체 데이터를 받아오지만, 코드가 `pageSize = 10`(기본값)으로 강제하고 있음 |
| **② Repository/Mapper 레벨 제한** | JPA `Pageable` 혹은 MyBatis `LIMIT` 절이 하드코딩돼 있음 | `PolicyRepository.findAll(Pageable pageable)` 혹은 MyBatis `<select …> LIMIT #{pageSize} OFFSET #{offset}` 와 같이 `pageSize`가 10으로 고정돼 있어 전체 건수를 구하는 별도 `COUNT(*)` 쿼리와 결과가 불일치 |
| **③ 총 건수와 실제 데이터 집합을 별도 쿼리** | `totalCount` 를 `SELECT COUNT(*) FROM POLICY …` 로 구하고, `list` 를 `SELECT * FROM POLICY … LIMIT 10` 로 구함 | 두 쿼리가 서로 다른 조건(예: 필터, 조인) 혹은 트랜잭션 격리 수준 차이로 인해 **동일 시점**의 데이터가 아니게 될 가능성이 있음 |
| **④ DTO/Response 매핑 오류** | `PolicySearchResponse` 에 `totalCount` 와 `policyList` 를 각각 다른 서비스 메서드에서 채워 넣음 | `totalCount` 는 전체 건수를, `policyList` 는 첫 페이지만 채워 넣어 **불일치**가 발생 |
| **⑤ UI 페이징 컴포넌트 설정** | 프론트엔드 그리드/테이블이 `pageSize=10` 으로 고정돼 있어 자동으로 첫 페이지만 렌더링 | 백엔드에서 전체 데이터를 반환하더라도 UI가 첫 10건만 보여줄 수 있음 |

> **가장 흔한 시나리오**  
> - **Spring Data JPA** 를 사용한다면 `Pageable` 객체가 `PageRequest.of(0, 10)` 로 고정돼 있거나, `Pageable` 파라미터가 `@RequestParam` 으로 전달되지 않아 기본값이 적용됩니다.  
> - **MyBatis** 를 사용한다면 매퍼 XML에 `LIMIT #{pageSize}` 가 하드코딩돼 있어 `pageSize` 가 10으로 고정됩니다.

## 2️⃣ 실용적인 해결 방법 (우선순위 별)

### ✅ 1순위 – UI → 백엔드 페이징 파라미터 흐름 점검
1. **프론트엔드** : “전체 조회” 버튼 클릭 시 `pageSize` 를 `null` 혹은 `0` 으로 전송하거나, `pageNumber` 를 `-1` 로 지정해 **전체 조회**임을 명시합니다.  
2. **Controller** : `@RequestParam(required = false) Integer pageSize` 로 받아 `pageSize == null || pageSize <= 0` 인 경우 `Pageable.unpaged()` 혹은 `Integer.MAX_VALUE` 로 변환합니다.  

```java
@GetMapping("/policies")
public ResponseEntity<PolicySearchResponse> searchPolicies(
        @RequestParam(required = false) Integer pageSize,
        @RequestParam(required = false) Integer pageNumber,
        // … 기타 검색 조건
) {
    Pageable pageable = (pageSize == null || pageSize <= 0)
            ? Pageable.unpaged()
            : PageRequest.of(pageNumber != null ? pageNumber : 0, pageSize);
    // 서비스 호출
}
```

### ✅ 2순위 – Repository / Mapper 레이어의 페이징 로직 정리
- **Spring Data JPA**  
  ```java
  // 전체 조회 시 페이지 제한을 없애는 메서드
  Page<Policy> findAll(Specification<Policy> spec, Pageable pageable);
  // 호출부
  Pageable pageable = (pageSize == null || pageSize <= 0) ? Pageable.unpaged()
                                                          : PageRequest.of(pageNumber, pageSize);
  Page<Policy> page = policyRepository.findAll(spec, pageable);
  ```
- **MyBatis** (XML 예시)  
  ```xml
  <select id="selectPolicies" resultType="Policy">
      SELECT *
      FROM POLICY
      <where>
          <!-- 검색 조건 -->
      </where>
      <if test="pageSize != null and pageSize > 0">
          LIMIT #{pageSize} OFFSET #{offset}
      </if>
  </select>
  ```

> **핵심** : `pageSize` 가 `null` 혹은 `0` 일 때 `LIMIT` 절을 **제거**하도록 조건을 추가합니다.

### ✅ 3순위 – 총 건수와 데이터 리스트를 동일 트랜잭션·동일 조건에서 조회
```java
@Transactional(readOnly = true)
public PolicySearchResponse search(PolicySearchCriteria criteria, Pageable pageable) {
    long total = policyRepository.countByCriteria(criteria);   // 동일 조건
    List<Policy> list = policyRepository.findByCriteria(criteria, pageable);
    return new PolicySearchResponse(total, list);
}
```
- **동일 메서드** 안에서 `count` 와 `list` 를 수행하면 **시점 차이**에 의한 불일치를 방지할 수 있습니다.

### ✅ 4순위 – 프론트엔드 페이징 컴포넌트 설정 검증
- 그리드/테이블 라이브러리(`ag‑Grid`, `DataTables`, `PrimeFaces` 등)의 **pageSize** 옵션이 고정돼 있지 않은지 확인합니다.  
- “전체 조회” 모드에서는 `pageSize` 를 `totalCount` 로 동적으로 설정하거나, **페이징 UI 자체를 숨김** 처리합니다.

### ✅ 5순위 – 테스트·모니터링 추가
1. **단위 테스트** – `PolicyService.search()` 에 대해 `pageSize=null` 일 때 전체 레코드가 반환되는지 검증.  
2. **통합 테스트** – 실제 DB에 18건이 존재할 때 API 호출 결과 `totalCount==18 && list.size()==18` 인지 확인.  
3. **모니터링** – API 응답에 `X-Total-Count` 헤더를 추가하고, 프론트엔드 로그에 `listSize` 와 `totalCount` 를 함께 기록해 차이 발생 시 알림을 받도록 설정.

### (1) Controller – 페이징 파라미터 정상화
```java
@RestController
@RequestMapping("/api/policy")
public class PolicyController {

    private final PolicyService policyService;

    @GetMapping("/search")
    public ResponseEntity<PolicySearchResponse> search(
            @RequestParam(required = false) Integer pageSize,
            @RequestParam(required = false) Integer pageNumber,
            PolicySearchCriteria criteria) {

        Pageable pageable = (pageSize == null || pageSize <= 0)
                ? Pageable.unpaged()
                : PageRequest.of(pageNumber != null ? pageNumber : 0, pageSize);

        PolicySearchResponse resp = policyService.search(criteria, pageable);
        return ResponseEntity.ok(resp);
    }
}
```

### (2) Service – 동일 트랜잭션·동일 조건에서 count & list
```java
@Service
@RequiredArgsConstructor
public class PolicyService {

    private final PolicyRepository policyRepository;

    @Transactional(readOnly = true)
    public PolicySearchResponse search(PolicySearchCriteria criteria, Pageable pageable) {
        long total = policyRepository.countByCriteria(criteria);   // 동일 조건
        List<Policy> list = policyRepository.findByCriteria(criteria, pageable);
        return new PolicySearchResponse(total, list);
    }
}
```

| 가능성 | 설명 | 확인 방법 |
|--------|------|-----------|
| **① 페이지 사이즈 고정** | `Pageable` 혹은 직접 만든 `limit` 값이 `10`으로 고정돼 있어 `SELECT … LIMIT 10` 형태의 쿼리가 실행됨. 총 건수(`totalCount`)는 별도 `COUNT(*)` 로 구해 18을 반환하지만 실제 데이터는 10건만 조회. | - 서비스 레이어 로그에 출력되는 SQL 확인<br>- `size` 파라미터가 어디서 설정되는지 디버그 |
| **② UI 바인딩 오류** | 서비스에서 18건을 모두 반환했지만 UI 모델(`policyTableModel`)에 `setData()` 호출 시 `subList(0,10)` 혹은 `for(i<10)` 로 제한하고 있을 가능성. | - `policyTableModel.setData()` 구현부 확인<br>- 화면에 전달되는 리스트 크기(`list.size()`)를 로그에 출력 |
| **③ 총 건수와 실제 데이터 불일치** | `totalCount`는 별도 `COUNT(*)` 로 구했지만, 실제 데이터 조회는 `LIMIT`이 적용된 쿼리를 사용. 따라서 “총 18건”은 맞지만, 실제 리스트는 10건만. | - `totalCount`와 `result.getContent().size()` 로그를 비교 |
| **④ 데이터 소스(외부 API) 제한** | 외부 시스템에 페이지당 최대 10건만 반환하도록 설정돼 있을 수 있음. | - 외부 API 호출 파라미터(`pageSize`) 확인 |

> **가장 흔한 원인**은 **① 페이지 사이즈 고정**이며, UI에 “전체 조회”라는 문구가 있더라도 백엔드에서 페이지네이션을 적용한 채 반환하고 있기 때문에 발생한다.

int pageSize = params.isFullSearch() ? Integer.MAX_VALUE : 10;   // 전체 조회이면 제한 해제

Page<Policy> result = policySearchService.search(params, pageable);

// 2) UI 바인딩 예시 (전체 리스트 전달)
policyTableModel.setData(result.getContent());   // subList 등 제한 코드 제거

## 📌 요약  

1. **주 원인** : 페이지네이션(`size=10`)이 전체 조회에도 적용돼 있어 실제 데이터가 10건만 반환되고, 총 건수는 별도 `COUNT(*)` 로 18건을 표시한다.  
2. **핵심 해결** : 전체 조회 시 페이지 사이즈 제한을 해제하고, UI 바인딩 로직에서 리스트 전체를 전달하도록 수정한다.  
3. **예방** : 테스트 케이스·코드 리뷰·설정 외부화·로그 모니터링을 통해 페이지 사이즈와 UI 바인딩 불일치를 사전에 차단한다.  

위 조치를 적용하면 “전체 조회” 시 화면에 18건 전체가 정상적으로 표시되고, 사용자에게 정확한 정보를 제공할 수 있습니다. 필요 시 추가 로그를 남겨 재발 방지를 확인하시기 바랍니다.
