## 🛠️ 3️⃣ 실용적인 해결 방안 (우선순위 별)

### 1️⃣ 페이지네이션 파라미터 검증·조정  
- **PSI 레이어**에서 `pageSize` 파라미터가 `null` 혹은 0일 경우 **전체 조회**를 의미하도록 `Integer.MAX_VALUE` 혹은 `-1`(MyBatis가 무제한) 로 변환한다.  
- **예시**  

```java
// PolicySearchPSI.java
@GetMapping("/policy/search")
public String searchPolicy(
        @RequestParam(value = "page", defaultValue = "1") int page,
        @RequestParam(value = "size", required = false) Integer size,
        Model model) {

    // size 가 없으면 전체 조회(무제한) 로 처리
    int pageSize = (size == null || size <= 0) ? Integer.MAX_VALUE : size;
    int offset   = (page - 1) * pageSize;

    List<PolicyDto> list = policySearchDSI.searchPolicies(offset, pageSize);
    int totalCount = policySearchDSI.countPolicies();   // 별도 COUNT 쿼리

    model.addAttribute("policies", list);
    model.addAttribute("totalCount", totalCount);
    return "policy/search";
}
```

### 2️⃣ 서비스‑DAO(DSI) 로직 점검  
- `searchPolicies(int offset, int limit)` 메서드가 **limit** 파라미터를 그대로 전달하고 있는지 확인한다.  
- **전체 조회** 시 `limit` 값이 `Integer.MAX_VALUE` 혹은 `null`이면 MyBatis 매퍼에서 `LIMIT` 절을 생략하도록 구현한다.  

```java
// PolicySearchDSI.java
public List<PolicyDto> searchPolicies(int offset, int limit) {
    if (limit == Integer.MAX_VALUE) {
        return policyMapper.selectAll();   // LIMIT 없이 전체 조회
    }
    return policyMapper.selectWithPaging(offset, limit);
}
```

### 3️⃣ MyBatis 매퍼 수정 (필요 시)  
- 매퍼 XML/어노테이션에 `RowBounds` 사용 시 기본값이 10으로 고정돼 있지 않은지 확인한다.  

```xml
<!-- PolicyMapper.xml -->
<select id="selectWithPaging" resultType="PolicyDto">
    SELECT *
    FROM POLICY
    ORDER BY POLICY_NO
    LIMIT #{limit} OFFSET #{offset}
</select>

<select id="selectAll" resultType="PolicyDto">
    SELECT *
    FROM POLICY
    ORDER BY POLICY_NO
</select>
```

### 4️⃣ 프론트엔드(Thymeleaf) 검증  
- `th:each` 로 반복되는 리스트가 `policies` 전체를 사용하고 있는지, 혹은 `th:if="${#lists.size(policies) > 10}"` 같은 제한 로직이 없는지 확인한다.  

```html
<!-- 예시: 전체 리스트 출력 -->
<table>
  <tr th:each="policy : ${policies}">
    <td th:text="${policy.policyNo}">...</td>
    ...
  </tr>
</table>
```

## 📌 6️⃣ 다음 단계 (실제 적용 가이드)

1. **코드 확인**  
   - `PolicySearchPSI`와 `PolicySearchDSI`에서 `pageSize`/`limit` 파라미터가 어떻게 전달되는지 정확히 확인.  
   - 매퍼 XML/어노테이션에 `LIMIT` 절이 하드코딩돼 있지 않은지 검토.

2. **임시 패치**  
   - 위에 제시한 **예시 코드**(PSI, DSI, 매퍼)와 같이 `size` 파라미터가 없을 경우 `Integer.MAX_VALUE` 로 변환해 전체 조회가 가능하도록 로직을 추가.

3. **테스트**  
   - **단위 테스트** : `searchPolicy` 메서드에 `size=null`·`size=10`·`size=100` 등 다양한 경우를 넣어 반환 건수가 기대값과 일치하는지 검증.  
   - **통합 테스트** : 실제 DB에 18건 이상의 테스트 데이터 삽입 후 전체 조회 API 호출 → 응답 리스트 길이와 `totalCount`가 동일한지 확인.

4. **배포 전 검증**  
   - 스테이징 환경에 적용 후 **전체 조회**와 **페이지별 조회**를 모두 테스트.  
   - 프론트엔드(Thymeleaf)에서도 리스트가 전체 출력되는지 확인.

5. **배포 & 모니터링**  
   - 수정된 코드를 배포하고, **응답 헤더**(`X-Result-Count`) 혹은 로그에 실제 반환 건수를 기록해 운영 중에 재발 여부를 모니터링.

- **심각도** : `HIGH` – 사용자는 실제 존재하는 데이터보다 적은 결과만 보게 되므로 업무 판단에 오류가 발생할 수 있습니다.

## 1️⃣ 근본 원인 상세 분석  

| 구분 | 가능성 있는 원인 | 설명 |
|------|------------------|------|
| **① 서비스‑레포지토리** | `policyService.search(params, PageRequest.of(0, 10))` 와 같이 **고정된 `Pageable`** 사용 | 페이지 사이즈가 10으로 고정돼 있어 `findAll(Pageable)` 호출 시 10건만 반환. 하지만 `count()` 쿼리는 전체 건수를 반환해 UI에 “총 18건”이라고 표시. |
| **② DAO / Mapper** | MyBatis 혹은 JDBC에서 `SELECT … LIMIT 10` 구문이 하드코딩 | 실제 DB에서 10건만 가져오지만, 별도 `SELECT COUNT(*)` 로 전체 건수를 구함 → 불일치 발생. |
| **③ UI / 프론트엔드** | “전체 조회” 버튼이 **페이지 1**(size=10)만 요청하고, **전체 건수**는 별도 API(또는 같은 API의 `totalElements`)로 받아 표시 | UI 로직은 정상인데, 백엔드가 페이지 사이즈를 10으로 제한해버림. |
| **④ 설정 파일** | `application.yml` 혹은 `properties`에 `default-page-size: 10` 같은 전역 설정이 존재 | 전역 설정이 적용돼 모든 리스트 API가 10건씩만 반환. |
| **⑤ 캐시/프록시** | 캐시된 페이지 결과(10건)만 반환하고, 최신 COUNT만 업데이트 | 캐시 무효화 로직이 누락돼 발생 가능. |

> **가장 흔한 시나리오**  
> - Spring Data JPA 사용 시 `Pageable`을 직접 생성하거나 `@PageableDefault(size = 10)` 어노테이션을 붙여 놓은 경우.  
> - MyBatis 매퍼 XML에 `LIMIT #{limit}` 파라미터가 고정값(10)으로 지정돼 있는 경우.

## 2️⃣ 실용적인 해결 방안 (우선순위 별)

### ✅ 1. 서비스·레포지토리 레이어에서 **페이지 사이즈를 동적으로 전달**하도록 수정  

| 단계 | 내용 | 참고 예시 (Spring Data JPA) |
|------|------|-----------------------------|
| 1‑1 | 컨트롤러에서 `size` 파라미터를 받아 `Pageable`을 생성 | ```java @GetMapping("/policies") public Page<PolicyDto> search(@RequestParam Map<String,String> params, @RequestParam(defaultValue = "0") int page, @RequestParam(defaultValue = "0") int size) { Pageable pageable = (size > 0) ? PageRequest.of(page, size) : Pageable.unpaged(); return policyService.search(params, pageable); } ``` |
| 1‑2 | 서비스 메서드 시그니처를 `Pageable`을 받도록 변경 | ```java public Page<PolicyDto> search(Map<String,String> params, Pageable pageable) { return policyRepository.search(params, pageable); } ``` |
| 1‑3 | 레포지토리(또는 Mapper)에서 `Pageable`을 그대로 전달 | ```java Page<Policy> findAllByCriteria(@Param("params") Map<String,String> params, Pageable pageable); ``` |
| 1‑4 | “전체 조회” 버튼 클릭 시 `size=0` 혹은 `size= Integer.MAX_VALUE` 로 호출해 **전체 데이터를 한 번에** 받아오게 UI 수정 | (프론트엔드 예시) `axios.get('/api/policies', { params: { page:0, size:0 } })` |

> **우선 적용** : 백엔드에서 `size` 파라미터를 **옵션**으로 받아, `size=0`이면 `Pageable.unpaged()` 로 전체 조회하도록 하면 기존 페이지네이션 로직을 그대로 유지하면서도 “전체 조회” 요구를 만족시킬 수 있습니다.

### ✅ 2. DAO / Mapper 레이어에서 **LIMIT** 구문을 파라미터화  

| 단계 | 내용 | 참고 예시 (MyBatis) |
|------|------|---------------------|
| 2‑1 | 매퍼 XML에 `LIMIT #{limit}` 를 사용하고, `limit` 파라미터를 메서드 인자로 전달 | ```xml <select id="searchPolicies" resultType="Policy"> SELECT * FROM policy WHERE … <if test="limit != null"> LIMIT #{limit} </if> </select> ``` |
| 2‑2 | 서비스에서 `limit` 값을 `null`(또는 0) 로 전달하면 전체 조회가 가능 | ```java List<Policy> list = policyMapper.searchPolicies(params, null); // 전체 조회 ``` |
| 2‑3 | COUNT 쿼리와 LIST 쿼리의 **조건이 동일**하도록 확인 (WHERE 절 동일) | ```xml <select id="countPolicies" resultType="int"> SELECT COUNT(*) FROM policy WHERE … </select> ``` |

### ✅ 3. UI/프론트엔드에서 **전체 조회** 시 페이지 사이즈를 명시적으로 지정  

| 단계 | 내용 | 예시 (JavaScript/React) |
|------|------|--------------------------|
| 3‑1 | “전체 조회” 버튼 클릭 시 `size` 파라미터를 `0` 혹은 `-1` 로 전송 (백엔드가 이를 해석) | ```js const fetchAll = () => { axios.get('/api/policies', { params: { page:0, size:0 } }).then(...); } ``` |
| 3‑2 | 페이지네이션 UI가 `totalElements` 를 사용해 페이지 수를 계산하도록 구현 (예: `Math.ceil(total/size)`) | ```js const totalPages = size > 0 ? Math.ceil(totalElements / size) : 1; ``` |

### ✅ 4. 전역 설정(`application.yml`)에 **기본 페이지 사이즈**를 명시하고, “전체 조회” 전용 프로퍼티를 별도 두기  

```yaml
spring:
  data:
    web:
      pageable:
        default-page-size: 10   # 일반 리스트에 적용
        max-page-size: 200
custom:
  pagination:
    all-size: 0   # 0이면 전체 조회
```

컨트롤러에서 `@Value("${custom.pagination.all-size}")` 로 읽어 `size == 0`이면 전체 조회 로직을 수행하도록 하면 설정만으로 동작을 제어할 수 있습니다.

### ✅ 5. 캐시/프록시 무효화 점검  

- **Cacheable** 어노테이션을 사용 중이라면 `@CacheEvict` 로 `count`와 `list` 캐시를 동시에 갱신하도록 설정.  
- **Redis** 등 외부 캐시를 쓰는 경우, `COUNT`와 `LIST` 키를 동일한 TTL 로 맞추거나, `LIST`가 업데이트될 때 `COUNT`도 함께 업데이트.

### (1) Spring Data JPA – 서비스·레포지토리

```java
// Controller
@GetMapping("/policies")
public Page<PolicyDto> searchPolicies(
        @RequestParam Map<String, String> params,
        @RequestParam(defaultValue = "0") int page,
        @RequestParam(defaultValue = "0") int size) {

    Pageable pageable = (size > 0) ? PageRequest.of(page, size) : Pageable.unpaged();
    return policyService.search(params, pageable);
}

// Service
@Service
@RequiredArgsConstructor
public class PolicyService {

    private final PolicyRepository policyRepository;

    public Page<PolicyDto> search(Map<String, String> params, Pageable pageable) {
        // 필요 시 파라미터 변환
        return policyRepository.searchByParams(params, pageable)
                               .map(this::toDto);
    }

    private PolicyDto toDto(Policy entity) {
        // 매핑 로직
    }
}

// Repository (Spring Data JPA)
public interface PolicyRepository extends JpaRepository<Policy, Long>, PolicyRepositoryCustom {
    // 커스텀 메서드 선언만 하면 구현은 아래 Custom 구현체에서
}

// Custom 구현체
public class PolicyRepositoryImpl implements PolicyRepositoryCustom {

    @PersistenceContext
    private EntityManager em;

    @Override
    public Page<Policy> searchByParams(Map<String, String> params, Pageable pageable) {
        // 동적 JPQL/CriteriaBuilder 사용 예시
        CriteriaBuilder cb = em.getCriteriaBuilder();
        CriteriaQuery<Policy> cq = cb.createQuery(Policy.class);
        Root<Policy> root = cq.from(Policy.class);
        // … WHERE 절 구성 …
        TypedQuery<Policy> query = em.createQuery(cq);
        if (pageable.isPaged()) {
            query.setFirstResult((int) pageable.getOffset());
            query.setMaxResults(pageable.getPageSize());
        }
        List<Policy> content = query.getResultList();

        // COUNT 쿼리
        CriteriaQuery<Long> countCq = cb.createQuery(Long.class);
        Root<Policy> countRoot = countCq.from(Policy.class);
        countCq.select(cb.count(countRoot));
        // … 동일 WHERE 절 …
        Long total = em.createQuery(countCq).getSingleResult();

        return new PageImpl<>(content, pageable, total);
    }
}
```

## 6️⃣ 마무리 체크리스트 (배포 전)

1. **서비스·레포지토리**에서 `Pageable`/`limit` 파라미터가 **고정값**이 아닌지 확인  
2. **통합 테스트**에 “전체 조회” 시 `size=0` (또는 `unpaged`) 로 호출했을 때 `totalElements`와 `content.size()` 가 일치하는지 검증  
3. **API 문서**에 `size=0` 옵션을 명시하고, 프론트엔드가 해당 옵션을 사용하도록 UI 수정  
4. **배포 후 모니터링**: `GET /policies?size=0` 호출 로그에 `totalElements`와 `content` 길이가 일치하는지 확인 (예: ELK, Grafana 알람)  
5. **회고**: 이번 이슈를 계기로 **페이지네이션 표준화 가이드**를 사내 위키에 추가

### 🎯 핵심 요점  

- **원인** : 백엔드 조회 로직이 페이지 사이즈를 고정(10)으로 제한하고, UI는 전체 건수를 별도 카운트만 받아와 표시 → 데이터 불일치 발생.  
- **우선 해결** : 서비스·레포지토리에서 `size` 파라미터를 동적으로 받아 **전체 조회**(unpaged) 혹은 원하는 페이지 사이즈를 지원하도록 수정.  
- **예방** : 코드 리뷰 체크리스트, 단위·통합 테스트, 전역 설정 관리, API 명세에 “전체 조회” 옵션 명시, 로그·모니터링 체계 구축.  

위 내용대로 수정·테스트·배포를 진행하면 현재 **10건만 표시되는 현상**이 사라지고, **전체 18건**이 정상적으로 화면에 표시될 것입니다. 필요 시 추가적인 로그 분석이나 DB 쿼리 프로파일링을 통해 미세 조정도 가능합니다. 🚀

## 1️⃣ 근본 원인 분석  

| 구분 | 가능성 | 근거 |
|------|--------|------|
| **① 페이지네이션(페이징) 설정 오류** | 조회 시 `limit 10` 혹은 `Pageable` 객체에 `size=10`이 고정돼 있음 | 대부분의 Spring‑MyBatis 연동 예제에서 `PageHelper.startPage(page, size)` 혹은 `Pageable`을 사용해 페이지당 건수를 제한한다. 현재 화면에 “총 18건”이 표시되는 것은 전체 카운트는 정상적으로 구했지만, 실제 데이터 리스트를 가져올 때 10건만 제한하고 있음을 의미한다. |
| **② 서비스‑DAO 로직의 조건 누락** | `SELECT … FROM … WHERE …` 구문에 `ROWNUM <= 10` 혹은 `FETCH FIRST 10 ROWS ONLY` 같은 제한 절이 포함 | 코드가 축약돼 있어 확인이 어려우나, “전체 조회”라는 명시적 요청에도 불구하고 제한 절이 남아 있을 가능성이 높다. |
| **③ 프론트엔드(Thymeleaf) 템플릿 오류** | `th:each` 로 반복할 리스트가 `page.content`(10건)만 전달되고, `totalElements`(18건)만 별도로 표시 | 백엔드에서 전체 카운트와 페이지 데이터가 각각 다른 모델 속성에 담겨 전달될 때, 템플릿이 페이지 데이터 대신 카운트만 사용해 리스트를 그릴 경우 발생한다. |
| **④ 캐시/세션 데이터 불일치** | 이전에 조회된 10건 캐시가 재사용되고, 총 건수만 최신 DB에서 조회 | 캐시 전략이 잘못 적용돼 있으면 이런 현상이 나타날 수 있다. 하지만 일반적인 CRUD 화면에서는 캐시 사용이 드물어 가능성은 낮다. |

**가장 유력한 원인** : **① 페이지네이션 설정이 고정값(10)으로 남아 있어 전체 조회 시에도 10건만 반환**하고, 총 건수는 별도 `COUNT(*)` 로 정상 계산되는 상황.

@Service

public class PolicySearchServiceImpl implements PolicySearchService {

    private final PolicyMapper policyMapper;

    @Transactional(readOnly = true)
